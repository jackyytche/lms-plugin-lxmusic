# M0.6 设计：多订阅源管理 + 音质降级/校验（全面对齐 PC 端语义）

> 起因（用户 2026-09-20 反馈）：①「订阅方式令人迷惑」——现在一个 textarea 同时接受"粘贴源"和"源 URL"，语义混在一起；② 需要**多订阅源聚合**能力；③ 音质选择的降级行为不明，担心"请求了源没有的码率/格式 ⇒ 无声"。
> 本文档 = 调研结论 + LMS 侧约束 + 定稿设计。实施见 HANDOFF §七。

## 一、PC 端（lx-music-desktop）权威语义

源码：`refs/lx-music-desktop`（本地全量克隆）。

### 1.1 音质阶梯与"裁剪"（不是盲请求）
- `src/common/constants.ts:82` — `QUALITYS = ['flac24bit','flac','wav','ape','320k','192k','128k']`（高→低，全局阶梯）。
- `src/renderer/core/music/utils.ts:221` — `TRY_QUALITYS_LIST = ['flac24bit','flac','320k']`（可选"最高档"）。
- `src/renderer/core/music/utils.ts:223-235` — `getPlayQuality(highQuality, musicInfo)`：
  ```
  type = '128k'                                   // 兜底
  if (用户档位 ∈ TRY_QUALITYS_LIST)
      list = qualityList[musicInfo.source]        // 该源声明支持的档位
      t = TRY_QUALITYS_LIST.slice(index(用户档位)) // 从用户档位往下
            .find(q => musicInfo.meta._qualitys[q] && list?.includes(q))
      if (t) type = t
  ```
  **结论：PC 端从"用户档位往下"逐个检查『该曲目实际具备的档位 ∩ 该源声明支持的档位』，取第一个命中的；一个都没命中才退 128k。它绝不会向源请求一个不存在的档位。**
- 歌单/下载侧同一逻辑：`src/renderer/worker/download/utils.ts:57` `getMusicType()`（`QUALITYS.slice(QUALITYS.indexOf(type))` 后取交集）。
- 每曲档位来源：搜索结果里就带 `meta._qualitys`（各平台 musicSearch/musicInfo 里 `types.push({type,size})`，如 `musicSdk/kw/musicSearch.js:50-51`）。
- 源支持列表来源：`src/renderer/core/apiSource.ts:40` `qualityList.value = musicSdk.supportQuality[apiId]`；用户自定义源则由源自己声明（`src/main/modules/userApi/renderer/preload.js:120-124` 的内置源示例即 `kw: ['128k','320k','flac','flac24bit']`）。
- 设置的界面顺序：`src/renderer/views/Setting/components/SettingPlay.vue:66` `[...TRY_QUALITYS_LIST,'128k'].reverse()` → 128k 在下、flac24bit 在上（用户选的是"上限"）。

### 1.2 取链失败怎么办：跨源换源（不是同源降档重试）
- `src/renderer/core/music/utils.ts:291-334` `handleGetOnlineMusicUrl()`：
  1. `targetQuality = quality ?? getPlayQuality(...)`（即 1.1 的裁剪）；
  2. `musicSdk[source].getMusicUrl(oldInfo, targetQuality)`；
  3. `.catch()`：**429（tooManyRequests）直接抛**（不换源）；否则若 `allowToggleSource` → 提示 UI → `getOtherSource(musicInfo)`（按歌名+歌手在**其他源**找同一首歌）→ 递归 `getOnlineOtherSourceMusicUrl({musicInfos: otherSource, retryedSource:[原源], ...})`。
- `src/renderer/core/music/utils.ts:237-286` `getOnlineOtherSourceMusicUrl()`：按 `musicInfos` 顺序找第一个"该曲有此档位"的候选源，`retryedSource` 去重，找不到就抛 `toggle_source_failed`。
- **结论：PC 端的"聚合"是『同一首歌跨源换源』，同源内部不降档重试**（降档在 1.1 已经通过裁剪避免了）。

### 1.3 其它已确认的 PC 行为
- 每个音质请求都会回传"实际拿到的 type"（`getMusicUrl` resolve `{url, type}`），PC 用它在 UI 上显示真实音质 —— 即**PC 端认为"源可能给了非请求档位"是正常现象，但一定要如实告知用户**。
- 自定义源在 PC 端是**替换 musicSdk**（`apis('kw').getMusicUrl` 这类）；运行时能力（平台/档位）由源在 `inited` 事件里声明。

## 三、定稿设计

### 3.1 数据模型
- **源文件**：`<prefsdir>/lxmusic/sources/<id>.js`（持久；id = 8 位 hex）。
- **元数据**（prefs `sourcesJson`，JSON 字符串，避免 prefs 里塞 64 KB 正文）：
  ```json
  [{"id":"a1b2c3d4","name":"独家音源","origin":"url","url":"https://.../6.js",
    "enabled":true,"added":1758300000,"bytes":64094,"sha1":"...","meta":{"version":"6","author":"w"}}]
  ```
  顺序即数组顺序 = 聚合优先级（设置页可上移/下移）。
- **迁移**：老的单源（`sourceContent`/`sourceName` + `/tmp/LXMusic/sources/current.js`）在首次启动时转成一条 `origin=legacy` 记录，正文写入持久目录，随后清空 `sourceContent`（一次性、幂等）。

### 3.2 设置页信息架构（解决"令人迷惑"）
```
① 订阅源 · 在线订阅
     [源 URL 输入框] [添加订阅]           ← 只做 URL 订阅
     说明：粘贴洛雪源的 http(s) 地址，插件下载后存为自己的源文件
② 订阅源 · 本地导入
     [文件路径输入框 class="stdedit selectFile"] [从文件导入]
     [目录路径输入框 class="stdedit selectFolder"] [导入目录内所有 .js]
     说明：点输入框右侧的浏览按钮可在服务器上选文件
③ 已注册的订阅源（统一列表，两种来源混排）
     每行：[启用✓] 名称（来源 URL/本地文件 · 大小 · 版本） [↑][↓] [删除]
     行内还可能显示：解析失败次数/最后错误（运行时回填）
④ 音质
     [上限档位 select] + [「源没有该档位时自动降到次一档」✓]（默认开）
     + [「取链后校验可播」✓]（默认开，HEAD 探测）
⑤ 桥接/并发/缓存（现有三项）
⑥ 封面代理 / 榜单源（现有）
⑦ 诊断：版本 / 引擎 / 源数量与状态 / 最近一次解析（源·档位·实际码率·耗时）
```

### 3.3 解析链（对齐 PC 语义 + 多源扩展）
```
resolve(track, 用户档位):
  ladder = QUALITYS[ from 用户档位 .. 128k ]                      # PC: slice(index)
  for q in ladder:                                                # 外层 = 音质（PC 的裁剪）
      for src in enabledSources:                                  # 内层 = 源（PC 无此层，扩展）
          if track.types 且不含 q: continue                        # PC: musicInfo.meta._qualitys[q]
          if src.declaredQualitys[platform] 且不含 q: continue      # PC: qualityList[source]
          if src 最近失败冷却中: continue                            # 防抖（新增）
          url, realQ = src.getMusicUrl(track, q)                   # 失败/429 → 记错误，换下一个
          if verifyUrl(url):                                       # HEAD 200 + audio/*（默认开）
              remember(track, q, src, url)
              report(realQ, 实际码率 = len*8/duration)             # 如实显示"实际音质"
              return url
  return 失败（附每个候选的错误，页面/队列可见，绝不静默）
```
- **不静默**：失败的候选逐个记 `why/source/quality/http code`，进日志 + 页面诊断块；协议处理器失败时给 LMS 一个明确错误而不是空 URL。
- **429 处理**（PC 同款）：整源短时冷却（默认 60s），不把它当作"换源理由"。
- **实际码率**：`Content-Length*8/duration` 估算；与请求档位不一致时在日志/队列元数据里标注 `（源降级: 128k）`。

### 3.4 兼容与开关
- 新 prefs：`sourcesJson`、`qualityFallback`(默认1)、`verifyUrl`(默认1)、`sourceCooldown`(60)、`builtinUrlSource`(见 §四 待定)
- 老 prefs 保留读取（迁移用），不再写入。
- 工具页（`index.html`）的粘贴导入保留为逃生通道（不放在设置页，避免again混乱）。

## 四、实现状态与结论（2026-09-20 收尾）

1. **"内置源"作为聚合兜底：不可行（已否决）**。我们 vendored 的 `engine/sdk/renderer/utils/musicSdk/api-source.js:11-19`
   里 `allApi = {}`（内置实现全被注释），`apis()` 对非 `user_api` 的源直接抛 `Api is not found`（:37）；
   vendor 树里也**没有** `*/api-temp.js`（PC 端 2.12.5 同样清空了内置源，见 `docs/lx-desktop-settings-forensics.md` §2.5）。
   ⇒ 内置 `getMusicUrl` 走不通，**取直链必须至少有一个启用的订阅源**；设置页在无源时明确红字提示。
   （用户当初选的是"默认关闭、设置页可开"——实际是不可做，这里记录更正。）
2. **PC 端设置里值得移植的项**（子 agent 全表见 `docs/lx-desktop-settings-forensics.md` §1/§4）：
   已做：多源列表+启用+顺序、音质上限、隐式自动降级、取链校验、每源元数据展示、两种导入路径（URL/服务器文件）。
   待议（按价值排序）：
   - **不喜欢歌曲规则**（`歌曲名@艺术家` 三态，服务端在出搜索结果前过滤）——契合度最高
   - **多平台聚合搜索 + 相似度重排**（PC `store/search/music/action.ts:23-32,91-111`；比"源聚合"更值得做）
   - `player.autoSkipOnError`（取链全失败 → 交给 LMS 跳下一曲的开关）
   - 直链/换源缓存语义（PC `otherSourceCache` 上限 10 条，>10 清空）
   - 繁简转换 `player.isS2t`（服务端做最省）、歌词三开关（LMS 歌词接口可支持）
   - 代理 `network.proxy.*`（Daphile 常在 NAS/代理环境）——LMS 侧影响 curl 环境变量
   - 热门搜索、来源名 real/alias、搜索历史（15 条）
3. **每源"最近失败冷却"**：已在设计里，**尚未实现**（当前靠"逐个候选依次试" + 缓存兜底；加冷却能避免连续点歌时反复撞死源）。
4. **实现落地**：见 HANDOFF §二/§四（0.7.0~0.7.2），验收脚本 `tmp/m0_6_acceptance.py`。
